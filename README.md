# Jev Cube Lab · 从逐步决策到魔方还原

**这个项目想验证：小模型能否学习魔方的操作规律，通过监督学习和强化学习，从简单状态逐步发展到还原随机打乱的三阶魔方。** 同时，用网页把模型每一步的选择、动作概率、状态变化和还原动画展示出来，让训练效果可以被观察和比较。

项目起初使用 Jev API 做逐步决策实验，现在增加了 Qwen3.5-0.8B 的本地训练路线。两部分目前独立运行：网页调用 Jev，本地脚本训练和评估 Qwen；训练后的 Qwen 尚未接入网页。本项目是独立研究实验，不是 Jev 官方项目，也不是 Jev RLCD 或原版 RLCR 的复现。

> **当前阶段：已完成浅层监督学习、第一轮 GRPO 小实验与探索信号诊断，已完成首批专家后缀课程数据准备及监督训练适配，尚无新阶段训练结果。尚未实现模型稳定还原随机三阶魔方。**
>
> 最近记录：2026-09-24。这里的还原率是实际闭环执行结果，不是训练集动作分类准确率。

## 项目要解决什么问题

魔方提供了一个规则明确、结果可验证的决策环境：模型只看当前状态，在 18 个合法动作中选择下一步；模拟器执行动作后，再把新状态交给模型，直到还原或达到步数上限。

我们希望依次回答：

1. **模型能否学会基本动作选择？** 用专家轨迹监督训练，在未见起点上验证是否能完整还原。
2. **强化学习能否带来额外收益？** 将模型自己的成功与失败转化为奖励，比较 RL 与继续监督训练的效果。
3. **如何从短路径推广到长路径？** 研究从终点附近开始的课程学习、专家纠正和错误恢复，缓解随机探索很难获得成功奖励的问题。
4. **模型自身能力与搜索帮助分别有多大？** 保留不加搜索的策略评估，后续单独设置固定搜索预算的对照。

核心目标是训练和理解模型的决策能力。求解器用于生成专家数据与验证解法；当前 Qwen 闭环评估时，不用求解器代替模型选动作。

## 已经取得的结果

### 1. 已跑通“训练 → 自主操作 → 实际还原”的流程

在相同的 **332 个浅层验证起点**上，每次最多执行 10 步，模型使用贪心动作，不加搜索或动作过滤：

| 训练方案 | 还原成功数 | 总还原率 | 三步状态还原率 |
|---|---:|---:|---:|
| 256 状态监督训练 | 132/332 | 39.76% | 31.25% |
| 完整轨迹展开后的 323 状态监督训练 | 185/332 | 55.72% | 49.61% |
| 扩充至 1000 状态监督训练 | 222/332 | 66.87% | 58.20% |
| 1000 状态监督模型＋20 轮 GRPO | 224/332 | 67.47% | 58.98% |

**已经观察到的进展：** 在这组实验中，展开完整轨迹、增加训练状态后，浅层验证还原率提升了。模型评估已从“下一步标签是否正确”推进到“能否连续操作完成还原”。

**仍不能下的结论：** GRPO 目前只净增加两个成功案例，且辅助 Brier 损失也更新共享主干，不能据此认定 RL 已带来稳定收益。不同监督实验的训练量和更新次数也不同。

以上是维护者在独立 H800 服务器上提供的单次运行记录，未附权重或完整原始运行日志；不是多随机种子统计。验证集已反复使用，起点未见不代表后续状态也未见，更不代表随机三阶魔方的还原率。完整口径见 [实验记录](docs/EXPERIMENTS.md)。

### 2. 找到了当前 RL 的主要瓶颈：有效奖励信号不足

首轮 GRPO 保留了 63 组、504 条轨迹，但只有 **6 组**同时包含成功与失败，20 轮中有 15 轮没有直接的组内奖励差异。

随后冻结模型，在同一批 256 个起点上做采样对照，每组 8 条轨迹：

| 采样温度 | 有效组数 | 每千次动作产生的有效组 |
|---|---:|---:|
| 1.0 | 11 | 1.17 |
| 1.6 | 21 | 2.26 |
| 2.0 | 30 | 3.23 |
| 2.5 | 35 | 3.74 |

提高温度在这次探测中增加了学习信号，但不等于已经提高还原能力。这也是后续转向课程学习的原因：让模型练习有机会成功的状态，而不是主要依靠更深状态上的随机试错。

### 3. 准备好了下一阶段的完整轨迹数据

已生成并逐步回放验证 **1000 个不同起点**：每个魔方随机打乱 30 次，由 cubejs 通用求解器求解。返回解法长度为 18～22 步，平均 21.697 步，保存了每一步动作和状态。

这批数据是专家示范，**不是模型的解题成绩**；解法长度不是最短距离，随机游走也不代表均匀随机状态。后续可以从轨迹后缀提取由近到远的练习。字段与生成方法见 [数据说明](data/README.md)。

## 后续计划

以下为待完成工作；第一项中的专家后缀分层、去重和初次划分已完成，随机游走补充及后续数据混合仍待实现。

| 顺序 | 计划 | 如何验证 |
|---|---|---|
| 1 | 将专家轨迹按“剩余解法步数”分层、去重；补充从还原状态出发的随机游走数据；划分训练、验证与最终测试集 | 检查轨迹正确性、状态重叠和每层独立状态覆盖；不把专家步数标成最短距离 |
| 2 | 建立混合难度课程，从末尾 1～3 步开始，逐渐加入 4～5 步，同时保留简单样本 | 在固定验证起点上检查新难度还原率和旧难度遗忘情况 |
| 3 | 对照继续监督训练与课程 GRPO；隔离置信度辅助损失的影响 | 从相同模型出发，记录数据量、训练成本，多随机种子比较真实还原率 |
| 4 | 收集模型走偏后的状态，由求解器提供纠正示范 | 检查循环率及失败状态恢复能力，避免只会沿示范路线执行 |
| 5 | 逐步扩展到独立随机起点，增加固定预算的搜索对照 | 分开报告纯策略成绩和模型＋搜索成绩，不混用指标 |
| 6 | 将本地模型接入网页，展示训练前后的行为差异 | 在相同起点下回放动作、轨迹和结果 |

是否继续增加难度由实验结果决定。若课程 GRPO 没有稳定优于监督基线，先改进数据覆盖与状态表示，而不是直接增加训练轮数。

## 快速运行网页

需要 Python 3.11+、Node.js 22+、npm 和 [uv](https://docs.astral.sh/uv/)。

```bash
git clone https://github.com/ZhangYelinglll/jev-cube-lab.git
cd jev-cube-lab
cp .env.example .env
# 编辑 .env，填写自己的 TYPESAFE_API_KEY
npm --prefix web ci
npm --prefix web run build
uv run --env-file .env python -m cube.server
```

打开 <http://127.0.0.1:8765>。远程服务器需要监听所有网卡时：

```bash
uv run --env-file .env python -m cube.server --host 0.0.0.0 --port 8765
```

该服务没有用户认证，不要直接作为公开 API 部署；访问者可消耗服务端的 Jev API 用量。远程个人使用可选择端口转发或限制网络访问。公开源代码不要求把运行服务暴露到公网。

Jev 网页会过滤立即逆操作和部分重复状态；本地 Qwen 评估没有这些过滤，因此两者成绩不能直接比较。网页显示的置信度不是还原成功率。使用细节见 [网页说明](web/README.md)。

## 训练环境与复现

已在独立 H800 服务器验证的环境：Python 3.11、PyTorch 2.6.0+cu124、Transformers 5.3.0。网页不需要安装训练依赖。请使用独立环境，并根据 GPU 驱动安装 PyTorch；以下对应 CUDA 12.4：

```bash
python -m venv .venv-train
source .venv-train/bin/activate
python -m pip install torch==2.6.0 --index-url https://download.pytorch.org/whl/cu124
python -m pip install -r requirements-training.txt
python -m cube.smoke --self-test
```

自行下载 `Qwen/Qwen3.5-0.8B`，将 `CUBE_MODEL` 指向完整的本地模型目录。实验使用非 Base 版本，模型权重不在本仓库分发，使用时遵守上游模型条款。

```bash
export CUBE_MODEL=/path/to/Qwen3.5-0.8B
CUDA_VISIBLE_DEVICES=0 python -m cube.smoke \
  --model "$CUBE_MODEL" --batch-size 2 --steps 1

CUDA_VISIBLE_DEVICES=0 python -m cube.train \
  --model "$CUBE_MODEL" \
  --data data/cube_trajectories_1000.jsonl \
  --output "runs/overfit-1000" --batch-size 8 --epochs 100

CUDA_VISIBLE_DEVICES=0 python -m cube.eval \
  --checkpoint "runs/overfit-1000/checkpoint" \
  --data data/cube_trajectories_expanded.jsonl --seed 17 --max-steps 10
```

注意评估命令刻意使用 **323 状态数据文件**来重建固定的 332 个验证起点，不要改为 1000 状态文件后直接比较结果。所有训练命令要求新的输出目录。

GRPO、探测实验和各阶段详细流程见 [TRAINING.md](docs/TRAINING.md)。目前 `cube/grpo.py` 的训练采样温度固定为 1.0；`python -m cube.probe --temperatures ...` 只做诊断，不改变训练策略。新的课程学习、有效组补采样、关闭置信度主干梯度等方案尚未实现。

## 数据与结果

仓库提供自动生成的魔方数据，不包含模型权重、API 响应日志或个人运行目录：

| 数据 | 用途 |
|---|---|
| `cube_shallow_256.jsonl` | 256 个精确距离 1～3 的状态 |
| `cube_trajectories_expanded.jsonl` | 展开专家路径并去重后的 323 状态 |
| `cube_trajectories_1000.jsonl` | 保留验证起点后扩充的 1000 状态 |
| `cube_random_1000/all.jsonl` | 1000 个随机打乱 30 次的状态与完整可行解 |

生成方法、字段与数据边界见 [数据说明](data/README.md)。最后一批解法长度为 18～22，**不是最短距离**，原始文件不区分训练／验证（派生划分见课程数据说明），需先展开成逐步样本，才能用于 `cube.train --curriculum`。

## 项目结构

```text
jev-cube-lab/
├── cube/                 # Python 服务、训练、评估与数据处理
│   ├── server.py         # Jev API 服务
│   ├── smoke.py          # 模型环境验证与共享动作定义
│   ├── train.py          # 监督训练
│   ├── eval.py           # 魔方模拟与闭环评估
│   ├── grpo.py           # GRPO 训练
│   ├── probe.py          # 探索信号诊断
│   ├── expand.py         # 专家轨迹逐步展开
│   ├── expand_1000.py    # 浅层数据扩充
│   └── curriculum.py     # 专家后缀课程数据准备
├── web/                  # 页面、动画、npm 依赖和前端检查
│   └── tools/            # JavaScript 数据生成工具
├── tests/                # Python 离线检查
├── data/                 # 已发布数据与字段说明
├── docs/                 # 训练指南与实验记录
└── .github/workflows/    # 自动检查
```

所有 Python 命令在仓库根目录使用模块方式运行。例如，旧命令 `python cube_train.py` 改为 `python -m cube.train`，旧命令 `python cube_eval.py` 改为 `python -m cube.eval`。前端命令改为 `npm --prefix web ...`。拉取新版本时保持完整目录结构；已有模型检查点和数据格式不变。
